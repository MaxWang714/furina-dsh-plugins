# LLM 主要功能与职责介绍稿

> 用途：向团队、评审者或合作方解释“LLM 在这个项目中到底负责什么”。本稿把本地素材（`llm-manager`、`cc-switch`、CLIProxyAPI 相关代码与数据）和此前项目设计讨论中的控制平面目标合并为一套可验收的说法。LLM 不是一个孤立的聊天窗口，而是一条可观察、可审计、可复盘的模型调用基础设施。

## 一句话定位

LLM 层负责把一次“需要模型能力的请求”可靠地送到正确的模型，并把请求的身份、流式过程、用量、耗时、成本、错误和隐私边界记录成可验证的事实；上层智能体负责决策，控制平面负责观察、管理、诊断和复盘。

## 主要功能与职责

### 1. 模型与供应商接入

统一接入不同供应商、账号、代理和本地模型，维护 provider/model 的可用性、能力标签和配置边界。调用方不应被每家 API 的字段差异绑死。

### 2. 请求协议与适配

把上游的统一请求转换为供应商协议，再把响应转换为统一结果。要区分非流式响应和流式响应，并保留工具调用、结束原因、错误和 usage 等语义。

### 3. 流式执行生命周期

对一次调用建立 `started → first meaningful token → usage/finish → completed/aborted/error` 生命周期。流式中间件必须保持原有 `AsyncIterable` 行为，不能因为观测而改变首 token 或结束语义。

### 4. 用量与 token 账本

记录输入、缓存命中、缓存写入、文本输出、推理输出和未分类 token。供应商没有提供 usage 时记为 unknown/null，绝不能用 0 假装“确实没有消耗”；输入与缓存、文本与推理的矛盾也必须显式标记。

### 5. 性能测量

区分 TTFB（网络/服务端首字节）与 TTFT（首个有意义 token）。同时记录总时长、生成速度和时间来源/置信度，避免把“收到元数据事件”误报成首 token。

### 6. 价格快照与成本核算

按 provider、model、token 类型和价格版本计算成本，支持倍率、前缀匹配和历史快照。价格未知、用量不完整或模型未登记时，成本应为 null/unknown，而不是 0；成本是可解释的估算，不是支付账单。

### 7. Observation 与调用审计

每次调用产生唯一 observation_id 和逻辑请求 ID，保存时间、模型、状态、token、TTFT、成本、错误码和 payload hash。它既用于仪表盘，也用于故障定位、回放、供应商比较和后续评估。

### 8. 会话、智能体和预设归因

一次调用要能归属到 agent、session、preset、task 等上层实体。默认只保存哈希或最小元数据，不把完整对话正文写入账本；这样才能回答“哪个智能体、哪个预设、哪个供应商导致了结果”，同时控制隐私风险。

### 9. 供应商健康与能力可见性

提供可用性、延迟、错误率、限流、模型能力和账号状态的观察入口。它可以支撑人工决策和未来的路由建议，但不能在缺乏证据时自动宣称“最优模型”。

### 10. 错误、取消与复盘

如实区分成功、供应商错误、插件异常和用户取消；保留脱敏错误信息和阶段时间线。结合诊断与 replay，可重放请求形状、比较不同模型并定位回归，但 replay 不应泄漏密钥或原始敏感正文。

### 11. 隐私、安全与保留策略

日志和 Observation 只保存完成任务所需的最小字段；错误中的 Bearer/API key/token 需要脱敏，session/trace 等敏感标识需要哈希。支持按天清理，保留策略不能以“永久保存”为默认答案。

### 12. 工具与可解释接口

通过工具暴露 usage 汇总、Observation 明细、清理策略和健康信息，让智能体或人工可以查询事实。工具的输出必须注明数据范围、时间窗和未知值语义，不能把猜测包装成观测结果。

## 与本项目其他组件的边界

| 组件 | 负责什么 | 不负责什么 |
|---|---|---|
| LLM/适配层 | 接入、调用、流式生命周期、usage、成本、Observation | 不替用户决定任务目标，不等于某一家模型 |
| DSH 插件 | 在 DSH 的 `llm/stream` 与工具层挂接观测、脱敏、离线记录和可选上报 | 不替 DSH 主智能体做规划，不持有独立密钥，不修改模型语义 |
| Vision/product | 桌面控制平面、Gateway、SQLite、Dashboard、Diagnostics、Replay | 不把 DSH 插件的运行时耦合进核心，不伪造供应商账单 |
| 智能体/上层应用 | 任务分解、工具选择、结果解释和用户交互 | 不应自行猜测 token、耗时或成本 |

## 对外介绍的 60 秒版本

“我们的 LLM 不是一个简单的聊天 API 封装，而是模型调用的可观测基础设施。它统一接入不同模型，保证流式调用不被破坏，分别测量首字节和首 token，准确记录输入、缓存、输出和推理 token，并基于带版本的价格快照计算成本。每次调用都会生成脱敏的 Observation，关联到会话和智能体，支持按供应商/模型/日期汇总、错误诊断和回放。未知 usage 就保持未知，未知价格就不报假成本；DSH 插件负责把这些事实接入 DSH，Vision 软件负责把事实展示和管理起来。这样我们先测量、再判断，先观察、再推荐。”

## 资料依据与限制

- `素材/llm-manager`：DSH `llm/stream` 中间件、JSONL 调用日志、usage/价格/健康/清理工具，是插件侧职责的直接原型。
- `素材/cc-switch`：供应商/账号切换、配置解析、代理与成本展示，支持“接入与管理边界”的判断。
- `素材/CLIProxyAPI`：协议适配、执行器、用量/价格插件和多账号管理，支持“统一协议与审计”的判断。
- `Vision/product`：Gateway、SQLite、Dashboard、Diagnostics、Replay，定义控制平面而不是 DSH 运行时的定位。
